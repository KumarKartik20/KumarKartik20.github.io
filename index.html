Core responsibilities

how the role breaks down day to day

A typical day begins with reviewing overnight job runs - verifying schedule outcomes through TWS logs and confirming that no pipeline has failed silently. From there, the work spans writing and refining SnowSQL transformations, maintaining Python-based reconciliation scripts, and coordinating with the operations team to resolve discrepancies between Snowflake and Vertica data stores.

A significant part of the role involves translating ambiguous requirements into concrete technical solutions - diagnosing the root cause behind a data quality issue, and replacing a manual, repetitive process with an automated one. That principle underlies most of the tooling referenced below: the Informatica XML extraction utility, the secure SFTP transfer wrappers, and the automated monitoring scripts were each built to remove a recurring manual step from the pipeline lifecycle.

Beyond pipeline development, the role includes ongoing collaboration with data engineering and operations teams to troubleshoot production issues, review pipeline health, and continuously refine existing workflows for better performance and lower long-term maintenance overhead.

How work moves
through my day.

Six stages, in the order they actually run.

01 / INGEST

Ingestion - ETL & SnowSQL pipelines

This is the front door of the pipeline. Batch feeds arrive as flat files and Oracle extracts, and I land them in Snowflake with SnowSQL and custom CTL files. The load stops in a governed staging layer first. The SnowSQL transforms that follow build the intermediate models everything else in the stream depends on.

Staging stays separate from the serving layer so a late file, a short file, or a changed layout fails somewhere it can be reloaded, instead of rewriting tables that are already being queried. The CTL contract and the transform steps are what make that ingest the same run every night, rather than a script someone edits by hand when it breaks.

Stable automated batch ingestion
02 / SCHEDULE

Orchestration - job scheduling

IBM TWS is what runs those steps in the right order. I author the job streams, the dependencies between ingest, transform, and publish, and the calendars they follow, then watch the overnight cycle so a failed or stalled job is visible before the morning handoff.

Where a stream used to sit until someone restarted it, I built fallback and recovery paths so the schedule can continue without that manual step. Keeping the stream definitions current as new feeds are added is part of the same work, and it is what holds on-time delivery at 99.8%.

99.8% on-time delivery
03 / TRANSFER

Transfer - secure cloud handoff

A lot of the estate still finishes on the on-prem Linux grid, while the next consumer expects a file in Azure Blob. I built SFTP wrappers that pick up those finished extracts and place them in Azure Blob Containers, with the transfer encrypted and the credentials rotated instead of left sitting in a script.

The wrappers are fault-tolerant on purpose. A dropped connection is retried, and a partial copy is not treated as a successful handoff. The blob is only trusted once the transfer has completed, which is the operating rule behind zero data loss on this path.

Zero data loss rotating credentials
04 / VALIDATE

Validation - data quality framework

After the transform, Snowflake and Vertica still have to describe the same data. I engineered a Python reconciliation suite that compares the two side by side, at column level, across runs of 75,000+ rows, and writes a variance report rather than a single pass or fail.

The report is where an investigation starts: which keys differ, which columns moved, and by how much. Row counts hide a bad cast, a filter that dropped the wrong slice, or an update that landed on only one platform. The column-level diff is what surfaces those before the batch is treated as production truth.

75,000+ rows reconciled per run
05 / MONITOR

Observability - monitoring & alerting

The first sign of a failure should come from the pipeline, not from the person waiting on the data. I designed a ksh monitoring engine that reads runtime metrics and job state from IBM Conman - what started, how long it ran, and how it ended - and publishes a morning summary operations can scan in one pass.

Thresholds are set so the alert fires while a rerun is still useful, before the SLA window closes. Read across successive mornings, the same summary also shows which streams are drifting slower. That is usually the earlier signal that a query or a growing file needs attention.

Alerts fire before SLA breaches
06 / MIGRATE

Migration - repository harvesting

Moving work off Informatica PowerCenter meant getting every mapping and session out of the repository. not a partial export done by clicking through the client. I built an automation engine that extracts those objects as XML, in parallel, then bundles them and dispatches the package with a status update.

That removed the manual extraction step entirely. In its place is a run that can be repeated and a bundle that can be reviewed, instead of a folder of files that depended on someone remembering each session and saving a current copy.

100% of manual extraction removed
